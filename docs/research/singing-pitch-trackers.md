# Open-source singing pitch trackers

Research date: 2026-11-01

## Recommendation

For the prerecorded *Japanese Denim* reference, run a controlled comparison of **RMVPE** and **torchcrepe** against the existing `librosa.pyin` contour. RMVPE is the best first candidate: it was designed specifically for vocal F0 in polyphonic music, can work on the original mix rather than depending entirely on Demucs, and its paper reports stronger raw-pitch and raw-chroma accuracy plus noise robustness. Its official code is Apache-2.0. [Paper](https://www.isca-archive.org/interspeech_2023/wei23b_interspeech.pdf) · [official repository](https://github.com/Dream-High/RMVPE) · [license](https://github.com/Dream-High/RMVPE/blob/main/LICENSE)

Use **torchcrepe** as the strong, easy-to-integrate monophonic baseline on the isolated vocal. It exposes frame-level pitch and periodicity, defaults to Viterbi decoding to reduce half/double-frequency errors, and includes silence, hysteresis, median, and mean filters. It is MIT-licensed. [official repository and usage](https://github.com/maxrmorrison/torchcrepe)

Use **Praat filtered autocorrelation** through Parselmouth as a diagnostic/reference track, especially when inspecting octave mistakes and note endings. Praat calls filtered autocorrelation its preferred method for intonation and explicitly exposes voicing, octave, octave-jump, and voiced/unvoiced path costs. It also provides a separate intensity contour, which is better evidence for line width than pitch confidence. Parselmouth calls Praat's C/C++ implementation directly, so its output matches Praat. Both are GPL, which is fine for a local research tool but needs care before bundling in a distributed product. [Praat method guidance](https://fon.hum.uva.nl/praat/manual/how_to_choose_a_pitch_analysis_method.html) · [pitch parameters](https://www.fon.hum.uva.nl/praat/manual/pitch_analysis_by_filtered_autocorrelation.html) · [Parselmouth](https://github.com/YannickJadoul/Parselmouth)

The final published curve should not be one tracker's raw output. Select/merge the reliable F0, retain the original 10 ms measurements, and derive a separate **perceptual display contour** with confidence-aware voiced boundaries and adaptive simplification. Loudness should come from a smoothed RMS/intensity envelope, not the pitch model's voicing confidence.

## Why the current contour can look wrong

The current workflow uses pYIN on a Demucs vocal stem, masks frames below a fixed voiced probability, applies its own octave correction, bridges gaps, smooths each segment, and finally extends note tails. Several distinct signals are therefore being conflated:

1. **Pitch and vocal presence:** low-confidence breathy or fading frames are deleted even when the note is perceptually continuing.
2. **Pitch and loudness:** pYIN probability measures certainty/voicing, not singing strength. RMS is the right starting point for width, ideally smoothed with attack/release constants rather than frame-by-frame.
3. **Source separation and F0:** a Demucs artifact can weaken the fundamental or emphasize a harmonic, causing an octave error. RMVPE on the full mix provides an independent track that does not share this failure mode.
4. **Raw measurement and teaching graphic:** micro-jitter should not become visible geometry, but real vibrato, scoops, and note transitions must remain. A fixed Gaussian blur cannot reliably distinguish them.
5. **Sustain and display:** carrying the final detected pitch for a fixed 250 ms fabricates a tail in some places and still truncates longer decays in others. The amplitude envelope should determine the visible tail while F0 confidence determines whether its pitch remains trustworthy.

## Proposed evaluation before changing the site again

1. Extract four synchronized candidates at 10 ms resolution:
   - pYIN on the Demucs vocal (current baseline);
   - torchcrepe `full` + Viterbi on the Demucs vocal;
   - Praat filtered autocorrelation on the Demucs vocal;
   - RMVPE on both the Demucs vocal and original mix.
2. Save every candidate's F0, voicing/confidence, and an independent RMS/intensity envelope. Do not overwrite the current published metadata.
3. Generate an internal A/B page for the coach-relevant phrases. Overlay the tracks, allow soloing each detector, and play ±2 seconds around disagreements over roughly 70 cents or any octave.
4. Manually mark a small truth set: flat sustains, rising/falling scoops, vibrato, quiet tails, breathy onsets, and octave-error cases. These examples matter more than one aggregate accuracy score for this teaching UI.
5. Pick the best primary tracker, then add conservative consensus correction: only replace a suspicious octave when two independent trackers agree and the replacement makes the local path continuous.
6. Build the display contour from the selected F0 with confidence-aware voiced regions and an adaptive simplifier. Preserve extrema for real scoops/vibrato; collapse pitch variation below a perceptual tolerance (for example 10–20 cents) on flat sustains.
7. Drive line width from a smoothed, phrase-relative dB envelope. Use slower release than attack so fades look continuous, and fade opacity when pitch becomes uncertain instead of inventing a long constant pitch.

## Phase 2 browser note

For live microphone pitch, low latency and causal processing matter more than matching the offline reference algorithm. Keep the planned `getUserMedia` → `AudioWorklet` design and benchmark a causal YIN/MPM implementation first. Basic Pitch TypeScript runs in the browser but evaluates buffered audio for transcription; it is not presented as an AudioWorklet streaming tracker. Essentia.js supplies WebAssembly audio-analysis bindings, but its AGPL/commercial terms need review. A small ONNX/CREPE-style model can be tried later if classical tracking fails on breathy singing. The offline reference and live user trace do not need to use the same detector as long as both are calibrated to Hz/MIDI/cents and their latency is accounted for.
